`schemas/studio.schema.json` 을 먼저 읽어라. 이 스키마를 한 글자도 벗어나지 마라.
피그마 플러그인이 이 JSON을 그대로 파싱한다. 키를 추가하거나 이름을 바꾸면 실패한다.

## 먼저 읽을 것

1. `prompts/E-style.md` — 카피 글자 수 상한과 구성 원칙. 여기를 어기면 피그마에서 글자가 잘린다
2. `examples/library/` — 톤 레퍼런스. `--ref product` 또는 `--ref info` 로 지정하면 그 파일만,
   지정이 없으면 전부 훑고 이번 건에 가까운 쪽을 따른다

레퍼런스는 **내용을 베끼는 게 아니라 톤과 구성 밀도를 맞추는 용도**다.
헤드라인 길이, 서브카피가 헤드라인을 어떻게 받는지, 요약 박스를 어디에 두는지를 본다.

## 재료

`docs/` 에 트랙 A 문서가 있으면 그것을 우선한다.
- `docs/A01-brief.md` → `prd` 항목
- `docs/A00-teardown.md` → `features`, `cards`
- `docs/A02-message.md` → `flow`, 카드별 `angle`과 `why`

문서가 없으면 `$ARGUMENTS` 또는 `input/` 폴더의 원본을 직접 읽어라.
`notes-` 로 시작하는 파일이 있으면 그게 이미지보다 정확한 근거다.

## 이 문서가 답해야 하는 것

완성된 카드뉴스 한 세트를 **제품으로 보고**, 그것에 대한 기획 문서를 역으로 복원한다.

| 산출 | 답하는 질문 |
|---|---|
| `prd` | 무엇을, 왜 만들었는가 |
| `features` | 이 세트는 어떤 구성 요소로 이루어져 있는가 |
| `flow` | 독자는 어떤 순서로 무엇을 느끼며 넘기는가 |
| `cards` | 각 카드는 어떤 구조인가 |

## 절대 규칙

1. **`cards`는 실제 카드를 그대로 옮긴다.** 개선안을 여기 섞지 마라.
   개선 아이디어는 `prd.improvements` 에만 넣는다. 둘을 섞으면
   "실제로 만든 것"과 "이렇게 했으면 좋았을 것"의 경계가 무너진다.
2. **`prd.improvements`는 2개 이상.** 자기 결과물의 약점을 짚는 항목이라 비우면 안 된다.
   이 항목이 문서 전체의 신뢰도를 만든다.
3. **`success[].metric`에는 측정 방법만.** 숫자를 넣지 마라. 실측은 플러그인이 `-`로 그린다.
4. 원문에 없는 인증 기관명, 수치, 효능을 만들지 마라.
5. `why`는 판단이어야 한다. "후킹 카드입니다" 같은 동어반복 금지.
6. 글자 수: `headline` 24자, `sub` 50자, `body` 항목당 34자.
   넘기면 피그마에서 글자가 프레임을 뚫고 나간다.

## features 구조

대분류 3~4개, 각각 자식 2~3개. 자식에는 관련 카드 ID를 붙인다.

```
1. 도입 설계
   1.1 후킹 카피        [C1]
   1.2 대표 액션 이미지  [C1]
2. 안전 근거 제시
   2.1 인증 기반 스펙    [C2]
```

번호는 재사용하지 않는다. 요소가 빠져도 번호는 비워둔다.

## flow 구조

`groups`는 독자 여정의 단계다. 진입 / 탐색 / 전환 정도로 3개 밴드가 적당하다.
각 그룹의 `nodes`는 왼쪽에서 오른쪽으로 흐르고, `edges`로 잇는다.
`type`은 `start`(시작) `card`(카드) `action`(행동) `exit`(이탈) 중 하나.

`dropoff`에는 **이탈이 가장 많이 날 지점과 그 이유**를 적어라.
이 한 줄이 유저플로우를 그림에서 분석으로 만든다.

## 출력

`specs/studio.json` 에 쓰고 **JSON 전문을 터미널에도 출력해라.**
사용자가 복사해 피그마 플러그인에 붙여넣어야 한다.

보고할 것: 카드 수, 기능 대분류 수, 플로우 노드 수, improvements 개수, 스키마 검증 결과.
참고 완성본이 `examples/studio.example.json` 에 있다.
